Timing instrumentation identified the earlier Core failures as **embedding waits**, not database opening: the reader opened SQLite in 13–18 ms and then remained inside embedding until its four-second bridge timeout. One desktop embedding wait caused **68.727 seconds of retrieval / 69.267 seconds of preparation**. The CPU embedding service recorded minute-long requests. Desktop refreshes could submit an entire collection at once and Core enrichment submitted batches of 64.

Local refreshes now yield every **four texts**, and process-local pending queries take priority over the next background batch. Core enrichment also uses four-text batches. Duplicate queries share a pending request; overlapping memory refreshes coalesce. Completed chunks survive later failures in the embedding cache, which distinguishes models/endpoints. Late results from cancelled queries never enter their cache, and a refresh cannot reintroduce vectors for memories deleted or edited while it was running. The caches hold vectors, never generated replies.

Desktop query waits cancel at **1,500 ms**; the Core reader allows **1,800 ms total embedding time**, retaining the outer four-second process bound. The configured current-memory fallback remains available. This bounds embedding waits rather than guaranteeing complete request latency: source changes can require a fresh read, and prompt assembly, generation, tools and repair have their own costs. A timed-out turn can lose semantic paraphrase matching and use keyword retrieval; durable memories are not dropped. Background HTTP batches have a ten-second bound. Cancellation cannot guarantee immediate resource release by a transport or external service that ignores it.

Core embeds context and latest-message focus together, with independent scoring and the existing per-render cache. All four memory blocks retain their order, duplicate suppression and source/epoch checks. Durable `synchronous=FULL` commits, receipts and state-only preparation optimizations from the prior release remain intact.

## Remaining limitations and evidence gaps

- **The one-second end-to-end call target is not yet demonstrated.** The eight final probes timed a prepared request through validated text and first server audio. Application state preparation, microphone endpointing/recognition, phone transport, buffering and audible playback were outside that measurement. First provider tokens remain private until validation completes; the 0.63-second median is not a user-visible response time.
- **Coverage is deliberately narrow.** Eligibility uses explicit English phrase patterns for standalone social, voice-feedback and short playful turns. Paraphrases, other languages, mixed requests, ambiguous follow-ups, images/files, tool history and special conversation modes can use the full slower path. Most substantive chat still uses MiMo Pro; substantive hands-free requests keep the existing local path. The request to speed up calls therefore enables fast small talk, not every spoken request.
- **The fast turn has less memory context.** It receives at most seven complete recent turns within 4,000 characters, the persona and selected current state/lessons. It skips archive, embedding and Core profile retrieval for that turn. Stored memory remains intact, and explicit memory requests keep retrieval, but an apparently standalone greeting may lose older conversational nuance.
- **Brevity is part of the speed gain.** The prompt normally asks for 6–12 words and at most two sentences; jokes get up to 30 words. Generation is capped at 128 tokens, and replies over 45 words are rejected. Extended creative writing, nuanced disagreement and long emotional responses are not represented by these timings.
- **A passed check is not a personality or truthfulness guarantee.** All three repeated final greetings returned the same “Hey. What do you want?” under the synthetic quiet-conversation context. This is a concrete repetition/abruptness issue, although the test did request a dry, direct tone. No broad evaluation of individuality, candid opinions, resistance to false premises, multilingual dialogue or long-session consistency was run for this new model path. The prompt and targeted output checks can reduce specific unsupported claims; they do not verify every statement.
- **Corrections and fallbacks still add delay.** Two of the eight final probes required a second private draft. Their text times were 1.86 and 1.89 seconds; first server audio was 2.10 and 2.13 seconds. The production 2.5-second limit applies to the first fast-provider word, not the whole response. Falling back to MiMo Pro or local Qwen adds more time. Only one quality escalation is allowed per task; it is not an unlimited chain through all specialists.
- **The sample is small and benefits from provider caching.** The final eight probes contain only six distinct prompts, and all reported cached prompt tokens (1,408–1,664). Cold-cache, long-session, noisy-call, interruption, peak-load and concurrent-load performance has not been established by this run. The observed maximum is not a worst-case bound. Model comparisons were taken at different times with small samples, so they establish which worked better here, not universal provider rankings.
- **Cloud availability and policy still apply.** Eligible call text/context goes to the direct cloud provider; local recognition/synthesis does not make all conversation processing local. Privacy restrictions, exhausted budgets, unavailable credentials or stale pricing can prevent cloud use and force a slower route or a refusal to escalate. The $0.50/task and $5/day limits remain active. The Sonnet specialist remains unavailable without an Anthropic key; coding uses the existing Kimi substitute. The routing checks did not perform a fresh paid end-to-end run through every specialist.
- **UltraSpeed remains unsuitable on the evidence collected.** Four of eight attempts across two comparisons timed out waiting 15 seconds for their first token; successful validated replies ranged from 2.32 to 14.25 seconds. Its speed here cannot be inferred from the provider's output-throughput claim.

The highest-value next validation is a real hands-free call measuring end of user speech to first audible response, followed by more varied dialogue and cold-cache trials. Repeated greeting quality should be improved without discarding the persona or weakening truthfulness checks. These are remaining recommendations, not changes made during this reporting review.
